# AW-Rocov v0.11 — Описание стратегии

Этот документ описывает алгоритм, реализованный в `AWRocov.mq5`, и является
источником истины по конечному автомату, триггерам, схемам роста объёма
усреднения и правилам выхода.

## 1. Назначение

AW-Rocov — это **только recovery**-советник:

- Он **не** генерирует входные сигналы.
- Он подбирает уже открытые позиции по символу графика (с фильтром
  по magic-номеру при `InpManageOnlyOwnOrders = true`) и трактует их как
  единую корзину.
- Его задача — вернуть корзину из плавающего убытка к небольшой плановой
  прибыли.

## 2. Понятия

- **Корзина** — множество позиций, удовлетворяющих условию
  `(символ, magic-или-любой)`. Снапшот корзины полностью пересобирается
  с состояния терминала на каждом тике, поэтому советник не несёт скрытого
  состояния относительно брокера.
- **Чистое направление** — `+1`, если `объём BUY > объём SELL`; `−1`, если
  наоборот; `0`, если объёмы равны.
- **Направление восстановления** — фиксируется в момент срабатывания
  триггера и удерживается на всём цикле восстановления. Совпадает с чистым
  направлением в этот момент. Все последующие решения о замке и
  усреднениях принимаются относительно него.
- **Базовый объём** `L_base` — суммарный объём «нетто-стороны» корзины в
  момент триггера. Используется как точка отсчёта для гармонической и
  линейной схем роста лота.
- **Точка безубытка** `P_BE` — цена, при которой плавающий PnL корзины
  обнуляется. Линейная аппроксимация:
  `P_BE = P_cur + (-floating_pnl) / (ppl × V_net)`,
  где `ppl = tick_value × point / tick_size`, `V_net = V_buy − V_sell`.
  Не определена при `V_net = 0` (полный замок).

## 3. Конечный автомат

```
            +-----------+
            | ОЖИДАНИЕ  |
            +-----+-----+
                  |  убыток >= порог  (и корзина не сбалансирована)
                  v
            +------------+
            | ЛОКИРОВАНИЕ|
            +------+-----+
                   | замок открыт (или пропущен на нетте)
                   v
        +-------------------+   найдена прибыльная позиция
        |    УСРЕДНЕНИЕ     | --------------------------+
        +---+--------+------+                           |
            |        ^                                  v
            |        |                    +-------------------------+
            |        +------------------- | ЧАСТИЧНОЕ_ЗАКРЫТИЕ      |
            |                             +-------------------------+
            |  потолок усреднений + use_be_hunt
            v
        +-------------------+
        |     ПОИСК_BE      | --(прибыльная позиция)--+
        +---+---------------+                          |
            |                                          v
            | PnL >= TP                  +-------------------------+
            v                            | ЧАСТИЧНОЕ_ЗАКРЫТИЕ      |
       +-----------------+               +-------------------------+
       | ЗАКРЫТИЕ_ВСЕХ   |
       +--------+--------+
                | все закрыты
                v
          +-----------+
          | ОЖИДАНИЕ  |
          +-----------+
```

### Переходы

| Из                    | Условие                                                | В                       |
| --------------------- | ------------------------------------------------------ | ----------------------- |
| `ОЖИДАНИЕ`            | `корзина не пуста И убыток >= порог И направление != 0`| `ЛОКИРОВАНИЕ`           |
| `ЛОКИРОВАНИЕ`         | `use_hedge_lock=false ИЛИ счёт неттинговый`            | `УСРЕДНЕНИЕ` (пропуск)  |
| `ЛОКИРОВАНИЕ`         | хеджирующий ордер успешно открыт                       | `УСРЕДНЕНИЕ`            |
| `УСРЕДНЕНИЕ`          | `floating_pnl >= basket_tp_money`                      | `ЗАКРЫТИЕ_ВСЕХ`         |
| `УСРЕДНЕНИЕ`          | прибыль какой-либо позиции >= порог частичного закрытия| `ЧАСТИЧНОЕ_ЗАКРЫТИЕ`    |
| `УСРЕДНЕНИЕ`          | `m_avg_count >= max_averaging_orders И use_be_hunt`    | `ПОИСК_BE`              |
| `УСРЕДНЕНИЕ`          | цена прошла `шаг` от последнего входа и потолок не достигнут | (остаёмся) добавляем усреднение |
| `ЧАСТИЧНОЕ_ЗАКРЫТИЕ`  | попытка частичного закрытия выполнена (успешно или нет)| `УСРЕДНЕНИЕ` (\*)       |
| `ПОИСК_BE`            | `floating_pnl >= basket_tp_money`                      | `ЗАКРЫТИЕ_ВСЕХ`         |
| `ПОИСК_BE`            | прибыль какой-либо позиции >= порог частичного закрытия| `ЧАСТИЧНОЕ_ЗАКРЫТИЕ`    |
| `ПОИСК_BE`            | `V_net = 0` (полный замок) ИЛИ застой > `stuck_seconds`| (остаёмся) forced close худшей |
| `ЗАКРЫТИЕ_ВСЕХ`       | попытки закрытия завершены                             | `ОЖИДАНИЕ`              |

> (\*) Если потолок усреднений уже достигнут и `use_be_hunt=true`,
> `УСРЕДНЕНИЕ` на следующем тике сразу же перейдёт в `ПОИСК_BE`.
> Эта «двойная транзитивность» оставлена сознательно — обработчик
> частичного закрытия не должен знать о существовании BE-охоты.

## 4. Триггер

Триггер срабатывает, когда выполнено **хотя бы одно** из условий:

- `убыток >= баланс × InpLossThresholdPct / 100`, при `InpLossThresholdPct > 0`
- `убыток >= InpLossThresholdMoney`, при `InpLossThresholdMoney > 0`

`убыток` равен `-floating_pnl` (положителен в красной зоне) и суммируется
по всей корзине, включая своп.

## 5. Замок

Если `InpUseHedgeLock = true` и счёт находится в режиме
`ACCOUNT_MARGIN_MODE_RETAIL_HEDGING`, открывается встречный ордер с объёмом
`|нетто_объём| × InpLockVolumeMultiplier`. На неттинговых счетах замок
молча пропускается (с предупреждением в лог), потому что хеджирование
там недоступно.

## 6. Усреднение

Новый усредняющий ордер добавляется, когда выполнены **все** условия:

- `m_avg_count < InpMaxAveragingOrders`
- цена прошла не менее `InpAveragingStepPoints` от `m_last_avg_price` в
  направлении, противоположном восстановлению (вниз — для лонг-направления,
  вверх — для шорт-направления)

Объём нового ордера определяется параметром `InpAveragingLotScheme`:

| Схема       | Формула                       | Сумма после `N`            | Поведение           |
| ----------- | ----------------------------- | -------------------------- | ------------------- |
| `GEOMETRIC` | `L_n = L_{n-1} × множитель`   | `~ L_base × mult^N`        | экспоненциальный    |
| `HARMONIC`  | `L_n = L_base / (n + 1)`      | `~ L_base × ln N`          | логарифмический     |
| `LINEAR`    | `L_n = L_base × (1 + n × k)`  | `~ L_base × N(1 + Nk/2)`   | под-квадратичный    |

`L_base` фиксируется в момент срабатывания триггера и равен суммарному
объёму нетто-стороны корзины. Параметры `InpAveragingLotMultiplier` и
`InpAveragingLotIncrement` влияют только на свою схему. Вычисленный объём
нормализуется к шагу/минимуму/максимуму лота символа. После успешного
открытия трекеры «последний» обновляются, счётчик усреднений увеличивается.

При `InpMaxAveragingOrders = 0` сетка усреднения отключена полностью —
после `ЛОКИРОВАНИЯ` автомат сразу попадает в `ПОИСК_BE`. В этом случае
`InpUseBEHunt` обязан быть `true` (проверяется в валидации параметров).

## 7. Частичное закрытие

Для каждой позиции корзины советник вычисляет:

- `прибыль_пункты(BUY)  = (Bid - цена_открытия) / point`
- `прибыль_пункты(SELL) = (цена_открытия - Ask) / point`

Если у какой-либо позиции `прибыль_пункты >= InpPartialCloseProfitPoints`,
автомат переходит в `ЧАСТИЧНОЕ_ЗАКРЫТИЕ` и закрывает `InpPartialClosePct%`
**первой** такой позиции через `CTrade::PositionClosePartial`. За один тик
делается одно частичное закрытие, чтобы умеренно ограничить активность
торговых запросов, после чего управление возвращается в `УСРЕДНЕНИЕ`.

## 8. ПОИСК_BE (BE-охота)

Это режим «recovery via redistribution»: новые рыночные ордера в этом
режиме **не открываются**. Цель — дотащить корзину до её собственной
точки безубытка `P_BE`, либо за счёт благоприятного движения цены, либо
за счёт снижения веса худшего элемента в средневзвешенной цене.

### 8.1. Расчёт BE

`P_BE = P_cur + (-floating_pnl) / (ppl × V_net)`

`ppl` = стоимость одного пункта движения цены для одного лота (в валюте
счёта), вычисляется как `tick_value × point / tick_size`. `V_net = V_buy −
V_sell`. Расстояние до BE в пунктах — `|P_BE − P_cur| / point`. Если
`V_net = 0`, BE не определён — корзина в «идеальном замке».

### 8.2. Отслеживание прогресса

В момент входа в `ПОИСК_BE` запоминаются `m_be_hunt_started_at` и текущее
расстояние до BE как `m_be_hunt_best_dist_pts`. На каждом тике:

- если `dist_pts + min_progress < best_dist_pts` (расстояние улучшилось
  на `InpBEHuntMinProgressPoints` или больше), `best_dist_pts` и
  `m_be_hunt_progress_at` обновляются;
- если `now − m_be_hunt_progress_at >= InpBEHuntStuckSeconds`, фиксируется
  застой и принудительно закрывается часть позиции с самым отрицательным
  плавающим PnL (см. 8.3). После этого трекер прогресса сбрасывается
  под новую конфигурацию корзины.

`InpBEHuntStuckSeconds = 0` отключает forced close — режим вырождается
в чистое ожидание благоприятного движения.

### 8.3. Forced partial close худшей позиции

Тикет с минимальным `POSITION_PROFIT + POSITION_SWAP` выбирается через
`CBasketManager::WorstPositionTicket()` и закрывается на
`InpBEHuntPartialClosePct` процентов. Если процент `>= 100`, позиция
закрывается полностью.

Математика выбора (для лонг-доминантной корзины, `V_net > 0`):

```
ΔP_BE = v_k × (P_BE_old − P_k) / (V_net − v_k)
```

Закрытие позиции с `P_k > P_BE_old` (т.е. купленной выше точки безубытка)
сдвигает `P_BE` **вниз**, к рынку. Поскольку самая убыточная BUY-позиция —
это, по построению, позиция с самым высоким `P_k`, выбор «худший по PnL»
эквивалентен «максимально приближающий BE к рынку». Для шорт-доминантной
корзины симметричное рассуждение даёт тот же результат.

### 8.4. Полный замок (`V_net = 0`)

Если в момент входа в `ПОИСК_BE` нетто-объём равен нулю (классический
полный замок), `P_BE` не определён, движение цены ничего не меняет. В
этом случае forced close выполняется немедленно, без ожидания таймера —
любая разблокировка корзины предпочтительнее бесконечного ожидания.

## 9. Выход из корзины

Как только `floating_pnl >= InpBasketTPMoney`, автомат переходит в
`ЗАКРЫТИЕ_ВСЕХ`, проходит по снимку списка тикетов и закрывает каждую
позицию. Контекст восстановления (направление, счётчики, BE-трекеры)
сбрасывается, и состояние возвращается в `ОЖИДАНИЕ`. Если какая-то
позиция не закрылась, её подберёт следующий тик — либо как новую
корзину, либо как новый цикл восстановления.

## 10. Безсостоятельность относительно брокера

Движок никогда не предполагает, что ордер, который он собирался открыть,
действительно существует. Каждый тик начинается с
`BasketManager::Refresh()`, перечитывающего позиции из терминала.
Единственное локальное состояние движка, переживающее тики:

- `m_state` (состояние автомата)
- `m_recovery_dir` (направление восстановления)
- `m_last_avg_price`, `m_last_avg_volume`, `m_avg_count`
- `m_base_volume` (для гармонической и линейной схем)
- `m_lock_done`
- `m_be_hunt_started_at`, `m_be_hunt_progress_at`,
  `m_be_hunt_best_dist_pts`, `m_be_hunt_partial_count`

Если EA перезапустить в середине цикла, он стартует в `ОЖИДАНИЕ` и
повторно активируется, как только условие триггера снова выполнится.
В v0.11 это сделано намеренно: персистентность состояния между
перезапусками вынесена в более позднюю версию.

## 11. Что **не** входит в v0.11

- Фильтры тренда / волатильности / новостей / времени дня
- Корзины из нескольких символов
- Генерация входных сигналов
- Сохранение состояния движка между перезапусками
- Графическая панель управления для прода (есть только тестовая)
- Адаптивный шаг сетки (`InpAveragingStepPoints` по-прежнему фикс)

## 12. Тестовая панель и внешние команды

Для отладки в Strategy Tester (визуальный режим) и на живом графике
советник рисует панель из 9 кнопок (см. README, раздел «Тестовая
панель»). Каждый клик не вызывает обработчик движка напрямую, а
**взводит один из request-флагов**:

| Флаг                   | Кто взводит      | Эффект в `Tick()`                                                |
| ---------------------- | ---------------- | ---------------------------------------------------------------- |
| `m_paused`             | `⏸ ПАУЗА`        | После `BasketManager::Refresh()` `Tick()` выходит немедленно. Никаких ордеров и переходов состояния. |
| `m_req_close_all`      | `✖ ЗАКР.`        | Переход в `REC_CLOSING_ALL` — на следующем тике `OnClosingAll` закроет всё. |
| `m_req_reset`          | `× СБРОС`        | `ResetRecoveryContext` + переход в `REC_IDLE`. Позиции не трогаются. |
| `m_req_force_trigger`  | `⚡ ТРИГГЕР`      | `ForceActivate()` — минуя `TriggerHit()`, входим в `REC_LOCKING`. |
| `m_req_force_be_hunt`  | `→ BE-HUNT`      | `ForceBEHunt()` — переход в `REC_BE_HUNT` из любого состояния, при необходимости поднимаем минимальный контекст. |

Запросы обрабатываются в начале `Tick()` **до** обычного `switch(m_state)`
и **до** проверки `m_paused`. Это значит, что:

- Запрос всегда исполняется ровно один раз и в детерминистский момент,
  даже если кнопка нажата на паузе.
- `OnChartEvent` никогда не правит `m_state` напрямую — нет конкуренции
  с регулярной обработкой состояния.
- В Strategy Tester сценарий «нажал → подождал тик → проверил состояние»
  поведённо предсказуем и пригоден для пошаговой отладки.

Кнопки `BUY/SELL` (фикстуры для создания корзины) идут мимо движка
полностью: EA напрямую дёргает `g_ops.OpenMarket()`. Это сделано, чтобы
не загрязнять контракт `CRecoveryEngine` тестовыми операциями.
